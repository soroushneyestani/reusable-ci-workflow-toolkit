# راهنمای عملی گردش‌کارهای بازاستفاده‌پذیر CI

**Reusable CI Workflow Toolkit** مجموعه‌ای از گردش‌کارهای GitHub Actions برای کنترل کیفیت، آزمون و ساخت نرم‌افزار است. یک مخزن Go و یک مخزن Java می‌توانند کد و تعریف build خود را نگه دارند و اجرای مرحله‌های مشترک را به همین ابزار بسپارند. در پایان اجرای موفق، مصرف‌کننده می‌تواند فایل ساخته‌شده را در همان اجرای CI دریافت و آزمایش کند. [نمای کلی پروژه](../README.md) · [قرارداد گردش‌کارها](SPEC.md)

## چه مسئله‌ای حل می‌شود؟

وقتی چند مخزن هر کدام فایل CI خود را از ابتدا می‌نویسند، تفاوت‌های کوچکی در نسخهٔ زبان، نحوهٔ اجرای آزمون، دسترسی توکن و نگهداری فایل خروجی ایجاد می‌شود. برای مثال، ممکن است یک تغییر روی برنامه‌ای Go در Linux آزموده شود ولی روی Windows بررسی نشده باشد، یا تیم Java نداند JAR بارگذاری‌شده همان فایلی است که آزمون‌ها روی آن اجرا شده‌اند. گردش‌کار مشترک، ترتیب مرحله‌ها و شکل خروجی را مشخص می‌کند و تغییر سیاست CI را قابل بازبینی می‌سازد. هر مخزن با انتخاب SHA مشخص کنترل می‌کند دقیقاً چه نسخه‌ای از این سیاست را اجرا کند.

این ابزار برای برنامهٔ Go با پکیج `main` در ریشه، برنامهٔ Java با یک POM در ریشه و یک JAR مشخص، و هر پروژه‌ای که یک اسکریپت اعتبارسنجی PowerShell روی Windows دارد، مسیر مستقلی ارائه می‌کند. کاربرد معمول آن بررسی درخواست‌های ادغام، گرفتن خروجی قابل اجرا برای بررسی و اجرای همان فرایند روی شاخهٔ اصلی است.

## گردش‌کار چگونه اجرا می‌شود؟

گردش‌کار **فراخواننده** در مخزن برنامه قرار می‌گیرد. رویدادهایی مانند `pull_request` تعیین می‌کنند که اجرا چه وقت آغاز شود. داخل `jobs`، کل کار با `uses` به یک فایل YAML بازاستفاده‌پذیر ارجاع داده می‌شود. گردش‌کار **فراخوانده‌شده** با `workflow_call` ورودی‌ها و خروجی‌هایش را تعریف می‌کند و ماشین اجرا، ترتیب کارها و سطح دسترسی job را مشخص می‌کند. یک composite action برای گروه‌بندی مرحله‌های یک job به‌کار می‌آید. این ابزار از گردش‌کار استفاده می‌کند چون انتخاب runner و کنترل چند job بخشی از قرارداد است. [روش استفادهٔ GitHub از گردش‌کارهای مشترک](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) · [تصمیم معماری](adr/0003-language-workflow-contracts.md)

| جزء | مسئولیت |
| --- | --- |
| [گردش‌کار Go](../.github/workflows/reusable-go.yml) | اعتبارسنجی ورودی روی یک ماشین ثابت، انتخاب Linux یا Windows، بررسی ماژول و ساخت یک برنامهٔ اجرایی |
| [گردش‌کار Java](../.github/workflows/reusable-java.yml) | نصب Temurin 21 روی Ubuntu، اجرای چرخهٔ Maven و تحویل یک JAR |
| [گردش‌کار Windows](../.github/workflows/reusable-verify.yml) | اجرای `scripts/verify.ps1` متعلق به مخزن فراخواننده و انتقال وضعیت خروج آن به CI |
| [مصرف‌کننده‌های نمونه](../fixtures/README.md) | دو برنامهٔ مستقل به همراه آزمون و job دریافت و اجرای خروجی |
| [اعتبارسنج محلی](../scripts/verify.ps1) | بررسی نحو YAML با Actionlint و اجرای بخش‌هایی از همان کد PowerShell روی ورودی‌های مصنوعی |

`checkout` کد مخزن فراخواننده را روی runner قرار می‌دهد. مرحله‌های PowerShell با همان درخت کاری اجرا می‌شوند و ابزارهای Go و Maven در آن به‌دنبال تنظیمات برنامه می‌گردند. فایل خروجی موفق در پوشهٔ موقت runner قرار می‌گیرد. عمل بارگذاری فقط مسیر فایل مورد انتظار را دریافت می‌کند. داده‌های بازگشتی از عمل بارگذاری، ابتدا به خروجی job و سپس به خروجی `workflow_call` تبدیل می‌شوند. job بعدی در مخزن مصرف‌کننده می‌تواند آن‌ها را از `needs` بخواند.

## شروع کار در یک مخزن مصرف‌کننده

برای بازتولید نمونه، محتوای `fixtures/go-caller/` یا `fixtures/java-caller/` را همراه با پوشهٔ پنهان `.github` به ریشهٔ مخزن آزمایشی مناسب منتقل کنید. در فایل فراخواننده، `FULL_TOOLKIT_SHA` را با SHA کامل کامیتی از ابزار که بررسی کرده‌اید جایگزین کنید. کامیت باید از مخزن عمومی همین ابزار باشد. در تنظیمات Actions مخزن فراخواننده، مجاز بودن استفاده از این گردش‌کار و actionهای آن را بررسی کنید. [تنظیم دسترسی در GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#access-to-reusable-workflows) · [راهنمای نمونه‌ها](../fixtures/README.md)

### نمونهٔ Go روی Linux و Windows

در ریشهٔ مخزن برنامه، `go.mod` و فایل‌های پکیج `main` را قرار دهید. `go.sum` را برای وابستگی‌های خارجی commit کنید. مقدار `go-version` باید نسخهٔ کامل مانند `1.27.4` باشد و حداقل `1.26.0` را رعایت کند. نسخهٔ انتخاب‌شده باید نیاز `go.mod` را هم برآورده کند.

```yaml
name: Go CI
on: [push, pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  linux:
    uses: soroushneyestani/reusable-ci-workflow-toolkit/.github/workflows/reusable-go.yml@FULL_TOOLKIT_SHA
    with:
      go-version: '1.27.4'
  windows:
    uses: soroushneyestani/reusable-ci-workflow-toolkit/.github/workflows/reusable-go.yml@FULL_TOOLKIT_SHA
    with:
      go-version: '1.27.4'
      runner: windows-2025
```

فراخوانی اول از `ubuntu-24.04` پیش‌فرض استفاده می‌کند. هر فراخوانی خروجی مستقل دارد. این انتخاب ابهام انتخاب خروجی از آخرین کار موفق یک ماتریس را برطرف می‌کند و فایل‌های هر سیستم‌عامل را با نام‌های جدا تحویل می‌دهد. بعد از کنترل ورودی و شناسایی پکیج `main`، `go vet` بررسی‌های ایستا را اجرا می‌کند و `go test -count=1` نتیجهٔ تست را دوباره به‌دست می‌آورد. مرحلهٔ ساخت یک باینری تولید می‌کند. `GOTOOLCHAIN=local` از انتخاب خودکار نسخهٔ دیگری از Go جلوگیری می‌کند و `GOWORK=off` اجرای ماژول ریشه را مشخص می‌کند. `-mod=readonly` از اصلاح خودکار `go.mod` جلوگیری می‌کند. [فایل کامل نمونهٔ Go](../fixtures/go-caller/.github/workflows/consumer.yml)

### نمونهٔ Java و Maven

مخزن Java یک `pom.xml` در ریشه دارد. در آن نسخهٔ compiler را با JDK 21 سازگار کنید و `<finalName>app</finalName>` را در بخش `<build>` قرار دهید. نمونهٔ همراه ابزار از JUnit برای آزمون واحد و از Checkstyle متصل به فاز `verify` برای بررسی شیوه‌نامهٔ کد استفاده می‌کند. افزونهٔ JAR کلاس `Main` را در manifest معرفی می‌کند تا خروجی نمونه مستقیماً با `java -jar` اجرا شود. [فایل POM نمونه](../fixtures/java-caller/pom.xml) · [چرخهٔ ساخت Maven](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle)

```yaml
name: Java CI
on: [push, pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  java:
    uses: soroushneyestani/reusable-ci-workflow-toolkit/.github/workflows/reusable-java.yml@FULL_TOOLKIT_SHA
    with:
      java-version: '21'
```

گردش‌کار روی Ubuntu از Maven نصب‌شده روی runner استفاده می‌کند و دستور `mvn --batch-mode --no-transfer-progress --strict-checksums clean verify` را اجرا می‌کند. `clean` خروجی قبلی را پاک می‌کند و `verify` مرحله‌های کامپایل، آزمون، بسته‌بندی و بررسی‌های متصل به چرخهٔ پروژه را اجرا می‌کند. سیاست lint را فراخواننده در `pom.xml` تعریف می‌کند. اگر Maven موفق باشد ولی `target/app.jar` فایل عادی مورد انتظار نباشد، کار شکست می‌خورد. [فایل کامل نمونهٔ Java](../fixtures/java-caller/.github/workflows/consumer.yml)

### استفاده از اعتبارسنج عمومی Windows

برای یک مجموعهٔ بررسی که در PowerShell نوشته شده، فراخوانی `reusable-verify.yml` کار ساده‌تری است. اسکریپت `scripts/verify.ps1` در مخزن فراخواننده و در PowerShell 7 با پروفایل غیرفعال اجرا می‌شود. صفر یعنی همهٔ بررسی‌های اسکریپت موفق بوده‌اند. خروج غیرصفر و فایل مفقود باعث شکست CI می‌شوند. ورودی اختیاری `go-version` نسخهٔ Go را پیش از اجرا نصب می‌کند. منطق lint، آزمون و ساخت را خود اسکریپت تعیین می‌کند. ## کش وابستگی‌ها و فایل‌های خروجی

کش به اجرای بعدی کمک می‌کند بخشی از دانلود وابستگی‌ها را تکرار نکند. گردش‌کارهای زبان فقط روی `push` شاخهٔ پیش‌فرض مخزن فراخواننده کش را فعال می‌کنند. Go از `go.sum` برای بخش محتوایی کلید کش استفاده می‌کند و در نبود آن کش را فعال نمی‌کند. در Java کلید Maven از فایل‌های پروژه مانند `pom.xml` و در صورت وجود تنظیمات مرتبط wrapper و extension استفاده می‌کند. کش خود JDK در گردش‌کار Java غیرفعال است. کش هر مخزن تابع محدودهٔ repository و ref در GitHub است. `hit` یعنی تطابق دقیق، `miss` یعنی کش دقیق پیدا نشده و `disabled` یعنی این اجرا از کش استفاده نکرده است. نبود کش نباید مانع ساخت از وابستگی‌های قابل دریافت شود. [مرجع وابستگی‌های کش GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) · [پیکربندی کش Java](https://github.com/actions/setup-java/blob/d1374f8ac74474200d16ef8ecee22c7ae7a51880/action.yml)

آرتیفکت محصول همان اجراست. نام `go-linux-amd64` برای `app`، نام `go-windows-amd64` برای `app.exe` و نام `java-jar` برای `app.jar` در تلاش اول استفاده می‌شود. تلاش دوم و بعدی پسوند `-attempt-N` دارند تا نام فایل‌های بارگذاری‌شده تکراری نشود. زمان نگهداری درخواستی هفت روز است. در job بعدی `artifact-name` برای دریافت فایل، `artifact-id` برای شناسایی در GitHub، `artifact-digest` برای SHA-256 آرشیو و `cache-status` برای مشاهدهٔ رفتار کش در دسترس‌اند. خروجی `artifact-digest` به آرشیو GitHub تعلق دارد. برای هش خود `app.jar` یا `app.exe` بعد از دانلود، SHA-256 همان فایل را محاسبه کنید. [رفتار بارگذاری و نگهداری GitHub](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md)

پس از باز کردن ZIP روی Linux ممکن است برای اجرای باینری Go به `chmod +x app` نیاز باشد. برای Java اجرای نمونه پس از استخراج با `java -jar app.jar` انجام می‌شود. job دریافت نمونه، دقیق بودن محتویات را کنترل می‌کند و پیام واقعی برنامه را با مقدار مورد انتظار مقایسه می‌کند. ## امنیت و مرز مسئولیت

- گردش‌کارهای قابل فراخوانی برای `push`، `pull_request` و `workflow_dispatch` طراحی شده‌اند. رویداد ورودی پیش از checkout بررسی می‌شود. گزینه‌های runner و نسخهٔ زبان از طریق قرارداد محدود می‌شوند. [الگوهای امن GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use)
- مجوز `GITHUB_TOKEN` در فایل‌ها `contents: read` است. اعتبار Git در تنظیمات checkout ذخیره نمی‌شود و گردش‌کارها secret فراخواننده درخواست نمی‌کنند. محدودهٔ cache و artifact در GitHub و سیاست مخزن فراخواننده برقرار می‌ماند. فایل‌های کش و آرتیفکت را محل نگهداری توکن یا دادهٔ محرمانه در نظر نگیرید.
- actionهای خارجی با SHA کامل فراخوانی می‌شوند. مسیر Go پیش از اجرای آزمون و ساخت، تاریخچهٔ checkout را با Gitleaks و وابستگی‌ها را با `govulncheck` بررسی می‌کند. نسخهٔ این ابزارها ثابت است و Gitleaks در گزارش مقادیر را پوشانده نگه می‌دارد. Maven اعتبار checksum دانلودها را با حالت سخت‌گیرانه بررسی می‌کند. این بررسی‌ها مسئولیت نگهداری وابستگی و ارزیابی کد فراخواننده را بر عهده نمی‌گیرند.
- تست‌های Go و افزونه‌های Maven کد مخزن فراخواننده را روی runner اجرا می‌کنند. بررسی pull request را با توکن خواندنی و بدون اعطای secret یا دسترسی انتشار انجام دهید. شاخهٔ اصلی را به موفقیت checkهای واقعی CI وابسته کنید و نام check را از نتیجهٔ یک PR نماینده بردارید. [دستورالعمل بررسی hosted و محافظت شاخه](HOSTED_VERIFICATION.md)

## چگونه نتیجه را راستی‌آزمایی کنیم؟

با PowerShell و Go در دسترس، اعتبارسنج اصلی ساختار workflowها و بخشی از قراردادهای اجرایی را بررسی می‌کند. برای آزمون کامل Java، JDK 21 و Maven را نیز روی `PATH` قرار دهید و آزمون Java را اجرا کنید. آزمون از برنامهٔ Maven نمونه استفاده می‌کند. موفقیت build، شکست JUnit، خطای Checkstyle و موفقیت Maven همراه با نام اشتباه JAR را جداگانه بررسی می‌کند. در مسیر موفق، هش نسخهٔ مرحله‌بندی‌شده را با فایل Maven مقایسه و JAR را اجرا می‌کند. حالت `-SkipMaven` فقط کنترل‌های ورودی و پیکربندی را اجرا می‌کند.

```powershell
pwsh -NoProfile -File scripts/verify.ps1
pwsh -NoProfile -File tests/java-contract.ps1
```

برای آزمون مستقیم هر نمونه، دستورات زیر را از ریشهٔ همان برنامه اجرا کنید.

```text
go vet ./...
go test -count=1 ./...
go run .
```

```text
mvn --batch-mode --no-transfer-progress --strict-checksums clean verify
java -jar target/app.jar
```

آزمون محلی مسیرهای شکست و ساخت را روی fixtureهای تکرارپذیر بررسی می‌کند. برای بررسی رفتار خود GitHub باید دو مخزن مستقل گردش‌کارها را با یک SHA مشخص فراخوانی کنند. ابتدا اجرای سرد شاخهٔ پیش‌فرض و سپس یک اجرای گرم روی همان ref را ثبت کنید. اجرای pull request سیاست کش غیرفعال را نشان می‌دهد. job بعدی هر اجرا فایل را از سرویس GitHub دریافت می‌کند و اجرا می‌کند. در شاخه‌های منفی می‌توان انتظار آزمون را تغییر داد یا `go.mod` و `pom.xml` را حذف کرد و نبود آرتیفکت را بررسی کرد. نتیجهٔ هر اجرا فقط برای SHA و بستر ثبت‌شده معتبر است. [دستورالعمل آزمون‌های hosted](HOSTED_VERIFICATION.md) · [شواهد انتشار](RELEASE_EVIDENCE.md)

در آزمون‌های ثبت‌شده، دو مخزن خصوصی مستقل Go را روی Ubuntu و Windows و Java را روی Ubuntu اجرا کردند. هر سه مسیر در تلاش اول `miss` و در تلاش دوم `hit` گزارش کردند. در هر تلاش، فایل‌ها پس از دانلود اجرا شدند. چهار اجرای منفی، شکست آزمون یا نبود فایل پیکربندی ریشه را تأیید کردند و آرتیفکتی نساختند. [نتیجهٔ اجراهای پیش از انتشار](RELEASE_EVIDENCE.md#hosted-evidence)

| Java کار را پیش از نصب JDK متوقف می‌کند | مقدار `java-version` باید رشتهٔ `'21'` باشد و یک `pom.xml` عادی در ریشه وجود داشته باشد. |
| JUnit و build می‌گذرند ولی Maven یا upload شکست می‌خورد | خروجی Checkstyle و دیگر بررسی‌های فاز `verify` را بخوانید. سپس بررسی کنید Maven `target/app.jar` را به‌صورت فایل عادی تولید می‌کند. |
| فایل خروجی در اجرای موفق پیدا نمی‌شود | نام برگشتی `artifact-name` را از همان run و attempt بخوانید و تاریخ انقضا و مجوز دانلود را بررسی کنید. |
| کش `miss` یا `disabled` است | نوع رویداد، شاخه و وجود `go.sum` را بررسی کنید. تغییر تعریف وابستگی یا انقضای کش ممکن است اجرای بعدی را سرد کند. |
| اعتبارسنج Windows ابزار را پیدا نمی‌کند | وجود `scripts/verify.ps1` و ترتیب ابزارها در `PATH` را کنترل کنید. برای Go می‌توانید نسخه‌ای را از طریق ورودی گردش‌کار نصب کنید. |

## هزینهٔ اجرا، محدودیت‌ها و درس‌های طراحی

اجرای جداگانه روی Windows و Linux امکان مشاهدهٔ شکست‌های مختص هر سیستم را فراهم می‌کند و زمان runner بیشتری مصرف می‌کند. زمان دانلود، صف GitHub و هزینهٔ تست با اندازهٔ برنامه و وضعیت کش تغییر می‌کنند. این پروژه عدد ثابتی برای افزایش سرعت ادعا نمی‌کند. خروجی Go برای پلتفرم انتخاب‌شده در همان اجرای CI است. Java این نسخه بر Maven، JDK 21 و یک JAR مشخص تمرکز دارد. ماژول‌های تو‌در‌تو، Gradle، runner سفارشی، امضای دیجیتال آرتیفکت و استقرار در محدودهٔ این قرارداد قرار نمی‌گیرند. [مرزهای پیاده‌سازی](SPEC.md)

سه تصمیم در ساخت ابزار اهمیت داشت. اول، قرارداد کوتاه و ثابت برای مسیرها و ورودی‌ها خطاهای پیکربندی را زودتر آشکار می‌کند. دوم، تست‌های منفی باید نشان دهند شکست آزمون یا نبود فایل واقعاً اجرای CI را متوقف می‌کند. سوم، بررسی وجود یک فایل در پوشهٔ build و دریافت و اجرای همان فایل از سرویس Artifact دو مرحلهٔ متفاوت‌اند. آزمون‌های محلی برای تکرار سریع خطاها به‌کار می‌آیند و نمونه‌های مستقل hosted صحت ارتباط بین مخازن، کش و تحویل فایل را نشان می‌دهند.
